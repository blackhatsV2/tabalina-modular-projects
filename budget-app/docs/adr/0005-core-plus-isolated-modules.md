# Small core plus isolated feature modules, not one monolithic `simulate()`

As the engine grew to cover income, bills, loans, an optional commute schedule, and flexible expenses, a single feature's bad data (a malformed loan, a corrupted bills section) could take down the whole simulation — exactly the kind of fragility the app's "rugged, doesn't lose data" goal rules out. Decided to split the engine into a small always-on core (profile data, date/money utilities, the period grid, balance + savings simulation) plus one isolated module per feature (`income`, `bills`, `loans`, `allowance`, `commute`, `flexibleExpenses`), each behind one shared contribute-events/costs/breakdown interface and independently enable-able.

`simulate()` runs each module in isolation: a module that throws, or whose contributed data fails its own zod schema, is excluded from the totals with a clear warning (e.g. "Loans couldn't be calculated: totals exclude them") rather than crashing the run or silently producing wrong numbers. The trade-off is real: a profile can now legitimately return a *correct-but-incomplete* result instead of a single pass/fail outcome, and every downstream consumer (screens, the parity test) has to treat "no warnings" as part of what "correct" means, not just the numbers themselves. In exchange, one broken feature degrades gracefully instead of taking the whole plan down — the same "rugged" property the app wants everywhere else (screens get error boundaries, sync/backup/reminders fail independently, for the same reason).

A side effect of modularizing this way: the old `dailySpending` tagged union (`allowance` XOR `commute`) is replaced by two independent modules, `allowance` and `commute`, each with its own `enabled` flag — consistent with every other module, and no longer a special-cased exception to the pattern.
